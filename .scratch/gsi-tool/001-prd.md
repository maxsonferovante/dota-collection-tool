## Declaração do Problema

Como jogador/observador de Dota 2 que precisa registrar o estado da partida em tempo real, quero uma ferramenta própria, instalada localmente, que receba os POSTs JSON enviados pelo client do jogo, persista cada frame em banco local e exponha um CLI que instala a configuração no Dota, gera o token de autenticação, liga/desliga o servidor e consulta os eventos — sem depender de serviços externos, sem leitura de memória do jogo e sem citar ou copiar implementações comunitárias existentes.

## Solução

Um workspace Rust com um servidor HTTP local que recebe os POSTs do jogo e responde 200 rapidamente, um núcleo de tipos tolerantes que cobre os 16 blocos da API (incluindo os 6 blocos que as implementações comunitárias não tipam), persistência assíncrona em SQLite (frames brutos + happenings derivados) e um CLI gestor com os comandos install, token, up, down, status e logs. Toda operação de I/O é assíncrona; a documentação e o código da ferramenta não mencionam nenhuma implementação de referência.

## Histórias de Usuário

1. Como jogador, quero instalar o arquivo de configuração via CLI, para não editar arquivos manualmente.
2. Como jogador, quero que o CLI detecte automaticamente meu diretório de instalação do Dota, para não precisar procurar a pasta de cfg.
3. Como jogador, quero sobrescrever o diretório detectado explicitamente, para suportar bibliotecas Steam customizadas.
4. Como jogador, quero que a instalação nunca sobrescreva uma config existente sem flag explícita, para não perder a configuração de outra ferramenta.
5. Como jogador, quero um backup de qualquer config substituída, para poder reverter.
6. Como jogador, quero gerar um token de autenticação novo via CLI, para que só meu client alimente meu servidor.
7. Como jogador, quero rotacionar o token, para que um token vazado pare de funcionar.
8. Como jogador, quero exibir o token atual, para confirmar qual valor está ativo sem adivinhar.
9. Como jogador, quero que o install injete o token ativo no arquivo de config, para jogo e servidor concordarem.
10. Como jogador, quero subir o servidor em foreground, para acompanhar durante testes.
11. Como jogador, quero parar o servidor em foreground com Ctrl-C de forma graciosa, para que frames em voo sejam gravados e não perdidos.
12. Como jogador, quero subir o servidor em background (detached), para continuar coletando enquanto jogo.
13. Como jogador, quero desligar o servidor detached via CLI, para não caçar PIDs manualmente.
14. Como jogador, quero consultar o status do servidor, para saber se a coleta está rodando e saudável.
15. Como observador, quero coletar os dados dos 10 jogadores enquanto especto, para que meu dataset cubra a partida inteira.
16. Como usuário, quero que cada POST recebido seja respondido imediatamente com sucesso, para que o jogo nunca trave esperando minha ferramenta.
17. Como usuário, quero que requisições com token errado ou ausente sejam rejeitadas, para que tráfego estranho nunca polua meu banco.
18. Como usuário, quero que cada frame aceito seja persistido com id da partida, tempo de jogo, tempo de relógio e timestamp de recebimento, para poder reproduzir a partida tick a tick.
19. Como usuário, quero o payload bruto preservado ao lado das colunas indexadas, para que campos futuros sobrevivam a patches.
20. Como usuário, quero os happenings derivados (kills, deaths, assists, transições dia/noite, mudanças de nível/cooldown de habilidades) guardados em separado, para consultar eventos sem varrer JSON bruto.
21. Como usuário, quero consultar os happenings filtrando por partida, tipo e limite, para achar rápido o que aconteceu.
22. Como usuário, quero acompanhar o log ao vivo, para ver os eventos durante a partida.
23. Como usuário, quero saída JSON nos logs, para encadear eventos com outras ferramentas.
24. Como usuário, quero logs operacionais no stderr com verbosidade ajustável, para execuções normais silenciosas e debug possível.
25. Como usuário, quero que o token nunca apareça nos logs, para que segredos não vazem no terminal ou em arquivos.
26. Como usuário, quero que a ferramenta continue funcionando quando frames chegam mais rápido do que o banco drena, para que teamfight quente não estoure memória nem bloqueie o jogo.
27. Como usuário, quero que frames excedentes sejam contados e despejados num arquivo local de overflow, para que nada se perca em silêncio.
28. Como usuário, quero que blocos vazios do jogo sejam tratados como ausentes e slots vazios de item como vazios, para que estados de menu/idle não quebrem o parsing.
29. Como usuário, quero que campos futuros desconhecidos sejam ignorados em vez de falhar, para que um patch do jogo não quebre a coleta.
30. Como usuário, quero que payloads Playing (objeto único) e Spectating (mapa time→jogador) sejam ambos aceitos, para que jogar e observar funcionem.
31. Como usuário, quero que posts de heartbeat sejam registrados, para distinguir jogo quieto de conexão morta.
32. Como usuário, quero descoberta de caminho Steam no Linux, Windows e macOS, para que a ferramenta funcione na minha máquina.
33. Como contribuidor, quero lints estritos e formatação aplicados, para manter o código limpo.
34. Como contribuidor, quero testes unitários e de integração com fixtures realistas anonimizadas de POST, para cobrir parsing, auth, semântica de buffer e fluxos do CLI.

## Decisões de Implementação

- Workspace com quatro crates: core (tipos de domínio mais parsing tolerante, sem dependência de runtime async), net (servidor HTTP), store (persistência SQLite assíncrona), app/cli (superfície de comandos mais ciclo de vida do servidor). Binário único; nenhuma biblioteca publicada.
- Servidor HTTP sobre o runtime async com framework de roteador e suporte a middlewares; um endpoint POST mais um endpoint de saúde; respostas de sucesso usam o content type que o jogo espera.
- Modelo de domínio cobre os 16 blocos da API como estruturas opcionais tipadas, mais envelope tipado para estados previous/added; apelidos de campo seguem os nomes do protocolo; todo parsing é total (sem panics em entrada desconhecida, vazia ou reordenada).
- Formato de persistência (síntese do grill; reduzido à decisão): uma coleção `frames` chaveada por (id da partida, tempo de jogo/relógio, recebido-em) guardando o payload bruto, mais uma coleção `happenings` (id da partida, tick, tipo, ator, detalhe) para eventos derivados; modo write-ahead; pool limitado.
- Formato de concorrência: fila única limitada em memória entre a camada HTTP e o worker de persistência; fila cheia descarta o mais antigo com contador e despeja o frame num log local de overflow; a camada HTTP nunca bloqueia no banco.
- Superfície do CLI: install (com nome, override de diretório, flags de force/backup), token (gerar/exibir/rotacionar), up (foreground por padrão, modo detached via flag com arquivo PID), down, status (PID mais saúde), logs (flags de partida/tipo/limite/follow/json).
- Tratamento do arquivo de config: escritor KeyValues próprio deste projeto; nome do arquivo segue a convenção de prefixo/sufixo exigida pelo jogo; ordem de detecção é registro/manifesto de biblioteca/manifesto do app no Windows e diretórios de dados Steam no Linux/macOS, com override explícito vencendo; restart do jogo é exigido após (re)instalar porque o client não recarrega a quente um endpoint já registrado.
- Autenticação: 32 bytes CSPRNG renderizados em hex, guardados em arquivo de config local ao lado do banco, injetados na config do jogo no install, validados por requisição; divergências são rejeitadas sem logar o segredo.
- Pré-requisito de inicialização do jogo: o client só emite com a flag documentada de integração na linha de comando (conforme atualização oficial de março de 2022, por motivos de desempenho quadro a quadro); o CLI informa esse requisito na saída do install.
- Taxonomia de erros: erros tipados por crate de biblioteca, erros contextuais livres só na borda do CLI; nenhum unwrap/expect em caminhos de I/O ou parsing.
- Regra de originalidade (dura): nenhum tipo, módulo, comentário ou doc desta ferramenta referencia qualquer implementação comunitária por nome, e nenhum código é copiado; o conhecimento do protocolo vem das notas de pesquisa próprias do projeto.

## Decisões de Teste

- O que faz um bom teste aqui: exercitar comportamento externo (status/corpo HTTP, exit code/stdout do CLI, linhas no banco), não internos; alimentar fixtures realistas anonimizadas de POST (idle, hero select, strategy, em-progresso, spectator de partida cheia, só-heartbeat); afirmar sobre frames persistidos e happenings derivados.
- Costuras mais altas para testar (codebase greenfield, então todas as costuras são propostas; confirme se alguma soar errada):
  1. Borda HTTP: POSTs representativos, afirma status/corpo e efeitos no banco incluindo 401 com token ruim.
  2. Borda CLI: roda subcomandos contra diretórios temporários (install grava arquivo correto mais semântica de backup; rotate invalida o antigo; ciclo up/down/status; filtros de logs).
  3. Borda store: rajadas concorrentes de frames drenam sem perda além do caminho contado de overflow; restart reprocessa o arquivo de overflow.
  4. Borda de parsing do core: bytes de payload entram, frame tipado sai — objetos vazios, campos desconhecidos, ambos os formatos Playing e Spectating, estados do envelope.
- Materiais prévios: nenhum no repo (greenfield; só notas de pesquisa em docs/). Fixtures devem espelhar os formatos já capturados nas notas (nomes de blocos, padrões de chaves dinâmicas, extras de spectator).
- Portões de qualidade: checagem de formatação, linter com warnings negados, suíte completa de testes a cada mudança.

## Fora de Escopo

- UI de analytics pós-partida ou sync remoto/nuvem; enriquecimento via APIs públicas de histórico de partidas.
- Leitura de memória do jogo, parsing de replays ou polling de APIs oficiais de partidas.
- Instalação como serviço do SO (units systemd/launchd) além do modo detached com arquivo PID.
- Hospedagem multiusuário, terminação TLS para endpoints remotos ou qualquer componente servidor central.
- Publicação de crate reutilizável; o binário do workspace é o produto.
